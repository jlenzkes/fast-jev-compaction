# This fork

A fork of [tamaratran/fast-jev-compaction](https://github.com/tamaratran/fast-jev-compaction), kept so that the changes below survive plugin updates. It installs as the same plugin, `fast-jev-compaction@fast-jev-compaction`, from this repository's marketplace.

Based on upstream `e3f262a7` (main as of 18 Sep 2026). Upstream's history is untouched; the fork's changes are the commits on top of it.

## What it changes, and why

**1. A reopened session keeps its compaction.** A message the compaction rebuilt kept the stored handle of the message it came from, and a reopen (`--resume`, or a reloaded VS Code window) followed that handle back to the full transcript, so the compaction was lost. Only a plain user message now keeps its handle. Taken from the `keepsHandle` condition in [myjunior/fast-jev-compaction@3625879](https://github.com/myjunior/fast-jev-compaction/commit/3625879). Measured on 9 Nov 2026: 168 of 168 kept messages present after compaction, 179 of 179 after a reopen.

**2. A dropped call leaves a stub.** Upstream [PR #83](https://github.com/tamaratran/fast-jev-compaction/pull/83) by its author, cherry-picked with authorship kept: when Jev rates a call as no longer needed, the call keeps its tool name and the head of its input, and its result becomes a truncation note, instead of the call and result being deleted.

**3. Stubs are the default.** PR #83 keeps deleting by default; this fork defaults `dropCalls` to `false`. A compaction that deletes calls leaves the model's own earlier reports with nothing behind them, and a session then repeats claims whose evidence is gone. An explicit `dropCalls` option still wins.

**4. A stub lasts one compaction.** A call an earlier compaction already cut to a stub - its result is this plugin's truncation note, and its input is already cut or short - is deleted when Jev still rates it as no longer needed (decision `stub_dropped`). Stubbing it again would cut nothing, so without this, stubs pile up: each compaction of a long session has less it can cut, until it falls under `minReductionRatio` and hands over to the built-in summary, and the session loses its verbatim history. Seen on 11 Nov 2026 in one session's fifth compaction, the second with stubs on: 411 calls stubbed, a 25% reduction against the 25% minimum, four Jev requests thrown away, then an 89-second built-in summary in place of the sub-second compactions before it. Jev is still asked about every stub (in windows when the history is long, change 6), and a stub it rates as still needed stays. A stub's result always carries a note `alreadyStubbed` recognizes: a result too short to truncate gets `[fast-jev-compaction stub]` appended, since without it a short-result stub was never seen as one and was stubbed again on every pass. `isCutResult` accepts only text this plugin produces - the note at the end, behind at most a `truncateHeadChars` head or a short result - so a tool output that quotes a note, as reading this repository does, is not taken for a stub. The reduction count leaves the stub note out, so a stub never counts as larger than the result it replaced and a history near `minReductionRatio` is not pushed under it.

**5. Where the host cannot compact, the plugin nudges instead of failing every turn.** VS Code and the desktop app run Claude Code as an SDK session, which refuses the `turn.complete` hook's `$.session.compact()` (upstream issue #150, open). Upstream logs `auto-compact skipped (...)` on every turn above `compactAtPercent`. The fork remembers the refusal and toasts `context at N%: type /compact at a natural stopping point` once on crossing the threshold, then again each further 10 points; a compaction, or context falling below the threshold, starts the count again. The threshold stays 60: in the session that prompted this, the operator's own `/compact`s landed between 57% and 67% of a 1M window, and the nudge only advises, so an early first nudge costs one line. Hosts that can compact behave as upstream does. Its tests are in `tests/hook.test.ts`.

**6. A history with more calls than one state can describe is asked in windows.** Each call costs the state about 39 tokens even as a one-line entry, so past roughly 630 calls `fitState` could not fit the 25k limit at any stage, threw `history too large for Jev`, and the hook fell back to the built-in summary; stubs made that a ratchet, because a stub is deleted only after Jev rates it. Taken from upstream [PR #119](https://github.com/tamaratran/fast-jev-compaction/pull/119) by deadczarvc (closed unmerged), applied as is: the calls are asked in contiguous windows, halved until each window's state fits, each keeping the goal, the first message, the pinned newest messages and its own messages; a call whose window cannot fit alone is not asked and stays, so nothing is removed without Jev. When the goal and the pinned messages alone do not fit, no window can, so that is checked once first and every call stays unasked. At most 8 requests are in flight, and a 429 or 5xx is retried once, immediately: no timer is confirmed in the hook runtime, which type-checks against plain ES2023, so there is no backoff. A history that fitted before is asked exactly as before. Replayed offline on 13 Nov 2026 with a stub Jev, on a rebuilt 807-call history that had fallen back: `windows:2`, every call asked, instead of the throw at ~31,936 estimated tokens.

**7. Prompts delivered beside a message are put back, and the compaction leaves a receipt.** Claude Code stores a prompt typed mid-turn, a subagent's report and a Stop hook's feedback beside another message, not as one; `session.compact` never lists them, and the host drops them with that message whenever it goes back without a handle - since change 1, every assistant message and tool result. Measured on 14 Nov 2026 on one 778-message compaction: the input reconstructed without those records reproduces the toast exactly (`72% reduction; 264 call_stubbed; state ~24988 tokens ... in 7 request(s)`), and 40 of the 42 records it held beside other messages did not survive, among them 7 subagent reports and 14 prompts the user typed mid-turn; the 2 that survived sat beside a plain user message. Over the 21 plugin compactions in 12 sessions from 9 Nov 19:36 on, a record survived exactly when it sat beside a plain user message for 1,141 of 1,167 such records; 1,039 were lost. The fork now notes each prompt `prompt.submit` sees arrive other than the user's own at an idle prompt, keeps that record per session in the plugin's store, and puts each back as a message of its own after the tool round it arrived in, as near as it can tell (the approach of [myjunior/fast-jev-compaction@1e706b6b](https://github.com/myjunior/fast-jev-compaction/commit/1e706b6b) for upstream #133, widened to deliveries that start a turn of their own). A put-back opens with a line the plugin writes, names its sender from the accepted origin and indents every delivered line, so a delivery cannot read as the plugin or as the user. The toast counts rebuilt and deleted messages instead of claiming every message survived, and the compacted history ends with a receipt that replaces the previous one and never reaches Jev. Limits: the plugin cannot see where the host stored a delivery, so a place is an estimate (measured on the same real records, 36 of 36 under one assumption about when `prompt.submit` fires, fewer under others), and the receipt marks the guesses; whether Stop hook feedback passes through `prompt.submit` is not established. Keeping assistant handles would have carried more but is change 1's and upstream #129's regression.

The plugin's tests were brought in line with changes 1 and 3, which upstream's tests still assert against.

## Deliberately not taken

- **ibernato's [1390ce1a](https://github.com/ibernato/fast-jev-compaction/commit/1390ce1a)** answers the same refusal by submitting `/compact` as a prompt when the session is idle. Not taken: it compacts at a moment nobody chose, possibly mid-task with background work running, and under change 4 each compaction deletes the stubs the previous one left, so compacting early costs history. Untested in VS Code whether a submitted `/compact` runs as a command.

- **Upstream PR #139** gives rebuilt messages their handles back, which undoes change 1.
- **Upstream PR #98** drops every handle, which also loses hidden reasoning and images kept on user messages.

## Taking upstream changes

```bash
git fetch upstream
git merge upstream/main
```

Then check that `keepsHandle`, the `dropCalls` default of `false` and `alreadyStubbed` survived the merge, in `hooks/fast-jev.ts`, `.claude-plugin/plugin.json` and `src/compact.ts`, and run `npm test`. Bump the version in `.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json` together, or `claude plugin update` will not see the change.
